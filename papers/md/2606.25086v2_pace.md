# PACE: Pullback Averaging Control for Efficient Optimization

## Core Idea

Many LM pipelines return an EMA of the training iterates instead of the final
iterate. The paper asks: given that the returned model is the iterate average,
how should the optimizer itself change to make that average better?

They formalize this as a linear-quadratic stochastic control problem:
continuous-time SGD on a quadratic `F(theta) = 0.5 (theta-mu)^T A (theta-mu)`
with additive noise, plus an additive control `u_t`, minimizing

```text
J(u) = E[ ||avg(theta) - mu||^2 + lambda * integral ||u_t||^2 dt ]
```

The optimal controller pulls the live iterate toward the posterior mean of the
optimum and toward consistency with the accumulated trajectory average. Two
approximations (`posterior mean ~= current EMA`, `t << T`) reduce it to

```text
u_t = T^-1 (I + lambda A^2 T)^-1 (ema_t - theta_t)
```

i.e. a pullback of the live weights toward their EMA, preconditioned inversely
in the curvature `A`. In practice `A` is unknown, so the diagonal Adam
second-moment estimate stands in for it, giving a clipped per-coordinate gain.
PACE is therefore AdamW plus one extra coordinate-wise operation per step and
one extra fp32 copy of the weights for the EMA.

Limits: `c -> infinity` recovers Lookahead with an inner loop of one step;
`c = 0` recovers AdamW (with EMA evaluation if enabled); `kappa = 1` recovers
uniform iterate averaging.

## Step Math

Per step `t`, per coordinate `i` (reference-code semantics):

```text
theta'      = AdamW.step(theta_t)            # decoupled wd, then m_hat / (sqrt(v_hat) + eps)
decay_t     = max((1 + gamma * max(0, t - rho))^(-kappa), 1e-4)
lam_i       = clamp( lr * c * decay_t / (sqrt(v_hat_i) + eps), max=1 )
theta_{t+1} = theta' + lam .* (ema_{t-1} - theta_t)     # pullback measured from PRE-step weights
ema_t       = (1 - decay_t) * ema_{t-1} + decay_t * theta_{t+1}   # every uf steps
```

Return / evaluate `ema_T`, not the live iterate.

Notes that matter for reimplementation:

- The pullback displacement is `ema - theta_t` where `theta_t` is the weight
  BEFORE the AdamW step of this iteration, so the Adam step is preserved
  additively and the update is a convex combination of the naive step target
  and the EMA point (guaranteed by the `lam <= 1` clamp).
- The same `decay_t` schedule is used both for the pullback gain and as the
  EMA interpolation weight `beta_t`. With the defaults `gamma = 1`, `rho = 0`
  this is the paper's `(1 + t)^(-kappa)`, floored at `1e-4`.
- Theory suggests gain `~ 1/v_hat`; the implementation uses
  `1/(sqrt(v_hat) + eps)` for stability. `eps` also floors the pullback
  denominator.
- The paper's Algorithm 1 gates both the pullback and the EMA update on the
  update frequency `uf`; the reference code applies the pullback every step
  and gates only the EMA update on `uf` (README documents the code behavior).
  Most paper experiments use `uf = 1`, where the two agree.
- `m`, `v`, `ema` (and an eval-swap buffer `theta`) are kept in fp32.

## Reference-Code Audit

Implementation in `papers/code/pace/src/pace/optimizer.py`, class `PACE`:

- Standard AdamW phase in fp32 with bias correction; decoupled weight decay
  applied as `p -= lr * wd * p` before the Adam step.
- Snapshots `p_before = p.data.clone().float()` before the step and computes
  the pullback from it: `p += lam .* (ema - p_before)`.
- `lam = clamp(lr * c * decay / (sqrt(v_hat) + eps), max=1)` computed by
  reusing the `v_hat_sqrt` buffer; clamping is optional via `clamp_pullback`
  (default on).
- EMA state is allocated when `use_ema_eval or lambda_pullback > 0` and
  initialized to the initial weights. EMA update:
  `ema = (1 - beta_t) * ema + beta_t * p` with `beta_t = decay_t`, gated on
  `ema_update_freq`.
- `optimizer.eval()` / `optimizer.train()` swap live weights with the EMA for
  validation (`use_ema_eval=True`); a `theta` buffer synced every step holds
  the live weights during the swap.
- `log_stats=True` records gain/clip-fraction/update-norm telemetry but does a
  GPU sync per stat; keep it off in benchmarks.
- Defaults: `lr=1e-4`, `betas=(0.9, 0.999)`, `eps=1e-8`, `weight_decay=0.01`,
  `c=0`, `beta_ema=0.01` (fixed-beta mode when `ema_kappa=None`), `gamma=1`,
  `rho=0`, `uf=1`.

## Local Benchmark Implementation

- Implemented in
  `workers/codex_noradam_confidence/experiments/run_wikitext_llm50m.py` as
  `PaceOptimizer`, a wrapper over any base optimizer, so it composes with the
  local PlainMuon, the `StackMuon` component ladder, and root `AnchorMuon`.
  Root `optimizer.py` is unchanged.
- Matches the reference update: pullback measured from the pre-step weights,
  gain `min(lr * c * (1+t)^(-kappa) / (sqrt(v_hat)+eps), 1)`, shared decay for
  gain and EMA beta with the `1e-4` floor, pullback every step, EMA update
  gated on `uf`.
- One deliberate deviation: the reference reuses AdamW's own second moment
  for the gain; the wrapper maintains its own `v` EMA of the (clipped)
  gradients (`beta2=0.999`) so the same gain definition applies over Muon
  bases. `precond="scalar"` drops the preconditioner as an ablation.
- The runner swaps to the EMA weights for every validation pass and the final
  full evaluation (`swap_to_ema()`/`swap_to_live()`), so PACE-family rows are
  scored on the returned model as the paper prescribes. `pullback_c=0` rows
  are the EMA-evaluated baselines (`emaeval_adamw`, `emaeval_muon`).
- Tests: `tests/test_pace_lm_runner.py` (hand-computed pullback steps, clamp
  transport, c=0 equivalence to the base optimizer, swap round-trip, uf
  gating, StackMuon component toggles).

## Experimental Settings In The Paper

- SFT: SmolLM2-1.7B, Qwen3-1.7B, Gemma3-1B on `smol-smoltalk` (1 epoch, seq
  1280, eff. batch 256), plus SmolLM2-135M dense sweeps and Qwen3-1.7B on
  Tulu-3. Pretraining: GPT-2-124M on FineWeb at the 2.5B-token Chinchilla
  budget (seq 1024, eff. batch 512, 4750 steps, TPU v6e).
- Training defaults: AdamW `(0.9, 0.999)`, `eps=1e-8`, `wd=0.01`, grad clip
  `1.0`, 50-step linear warmup then constant LR unless testing decay, bf16.
- Headline SFT settings (Fig 1): SmolLM2-1.7B `lr=1e-3, c=0.15, kappa=0.2`;
  Qwen3-1.7B `lr=5e-4, c=0.25, kappa=0.5`; Gemma3-1B `lr=1e-3, c=0.15,
  kappa=0.5`; all `uf=1`, baselines given their best schedule (cosine/WSD).
- Pretraining: best `c ~= 3e-3` at `eta = 2e-3` under constant, cosine, and
  WSD alike (robust band `1e-3 <= c <= 3e-3`); `kappa in {0.2, 0.5}`.
  PACE+WSD best overall (`3.507 +/- 0.006` vs constant-LR PACE `3.537`);
  PACE at constant LR roughly matches AdamW+WSD (`3.537` vs `3.531`) and
  beats every shorter-budget WSD branch at equal tokens.
- Sensitivity: optimal `c` is stable across LR, `kappa`, and
  `uf in {1, 5, 10}`; improvement over EMA-evaluated AdamW holds across the
  swept ranges. Clip fraction is large only for big `c` / small `kappa`,
  mostly early in training.
- Competitive with Schedule-Free at equal LR budget, and faster per wall-clock
  in their setup (no fast/slow averaging switch); SF holds one fewer weight
  copy.
- Multi-seed checks (3 seeds) preserve the method ordering in both SFT and
  pretraining; headline runs are single-seed.

## Benchmark Implications For This Repo

- PACE is defined around AdamW: the pullback gain reuses Adam's `v_hat`. Base
  Muon has no per-coordinate second moment, so a Muon adaptation must choose a
  gain preconditioner. Reasonable options, closest-to-theory first: reuse
  NorMuon's post-GramNS row second-moment (row-broadcast gain), maintain a
  dedicated `v` EMA of raw grad^2 only for the pullback (adds one state
  tensor), or drop the preconditioner and use a scalar clipped gain
  `min(lr * c * decay_t, 1)`. The paper's own discussion flags
  Muon-preconditioned pullback as open future work.
- The fallback (scalar/vector) path in the local stack is already Adam-shaped
  (`atan2`/RMS moments), so the reference gain formula ports directly there.
- PACE's evaluation contract is different from every optimizer currently in
  the runners: validation and the final model must use the EMA weights.
  Runner integration needs `optimizer.eval()`-style swaps around validation
  (the LLM EMA-Nesterov wrapper already restores base weights before
  stepping, so there is precedent for swap discipline in the harness).
- Interaction with SODA is the interesting scientific question: SODA pulls
  toward the initialization anchor, PACE pulls toward the trailing EMA. Both
  are per-step contraction terms; stacked naively they may double-regularize,
  and PACE may substitute for SODA's late-training stabilization.
- Interaction with the WSD schedule matters: the paper sells PACE partly as a
  decay-free alternative, but its best pretraining number still used WSD, so
  local runs should keep WSD and also try constant-LR PACE arms.
- Distinct from the local EMA-Nesterov wrapper: EMA-Nesterov does a lookahead
  extrapolation along the EMA direction and trains/evaluates live weights;
  PACE interpolates toward the EMA inside the step and returns the EMA.

## Risks

- Memory: one extra fp32 weight copy for the EMA (the reference code holds a
  second `theta` buffer too, only needed for eval swapping).
- Early-training clamp saturation: `v_hat` is tiny at first, so `lam` hits the
  clamp and coordinates transport fully to the EMA. With warmup and `uf=1`
  this is benign in the paper, but with Muon-scale LRs (`~1e-3` matrix LR vs
  AdamW `1e-4`) the pre-clamp gain is larger; `c` grids must extend low.
- Small `kappa` keeps `beta_t` large late in training, so the EMA tracks the
  live iterate closely and the returned average loses its variance-reduction
  benefit; large `kappa` freezes the EMA early. The floor `beta_t >= 1e-4`
  bounds the freeze.
- The pullback gain uses the trainer-visible `lr`: under WSD decay the
  pullback strength decays with the schedule as designed, but a separate
  fallback LR (as in the local stack) changes the effective `c` on that path.
- Single-seed headline results in the paper; local conclusions should follow
  the repo's HPO-then-replay protocol before claiming a new best optimizer.
